# 07 · 400×300 能跑多快？Godot 2D 游戏怎么落地？

> 前提变了：**不做阅读器，做一台跑自己 2D 游戏的高刷墨水屏掌机**。这篇算两笔账：刷新率够不够，Godot 工程能不能搬。

## 1. 刷新率：把账算清楚

### 1.1 一帧的时间由两部分串起来

```
T_frame = 传输时间 + 面板扫描时间
          30 KB / SPI 时钟      300 行 × 行周期
```

- **传输**：双平面各 400×300/8 = 15 000 B，共 30 KB；
- **扫描**：400×300 有 300 个栅极行，行周期估 50–106 µs（1.54" 的 SSD1681 实测 106 µs/行）；
- 两者**串行**：控制器在刷的时候不收新数据。

### 1.2 算出来是这样

| SPI 时钟 | 传输 30 KB | 扫描 15 ms（乐观） | 扫描 30 ms（保守） | 帧率（乐观） | 帧率（保守） |
|---|---|---|---|---|---|
| 10 MHz | 24 ms | 39 ms | 54 ms | 26 fps | **19 fps** |
| 20 MHz | 12 ms | 27 ms | 42 ms | 37 fps | **24 fps** |
| 40 MHz | 6 ms | 21 ms | 36 ms | 48 fps | **28 fps** |

**结论：400×300 全屏 1bit 的现实区间是 18–28 fps，最乐观 30 fps 出头。**

`SPI 时钟` 是这里唯一你能直接优化的大头：微雪的树莓派例程用 10 MHz，UC8176 手册上限通常在 20 MHz 量级，ESP32-S3 跑 20–40 MHz 需要实测误码。

### 1.3 三个还能再挤的杠杆

| 杠杆 | 收益 | 代价 |
|---|---|---|
| **局部窗口**：只刷变化的行 | 传输和扫描同比缩短 | 窗口外不能有内容变化 |
| **4 灰 → 1bit** | 传输减半 | 没有灰阶，只能抖动 |
| **降分辨率渲染**（如 320×240 居中缩放） | 按像素比例提速 | 画面变糊（1bit 屏上尤其明显） |

例：游戏区只占 400×240（240 行），SPI 20 MHz → 传输 9.6 ms + 扫描 24 ms ≈ 34 ms → **29 fps**。

### 1.4 一个更重要的数字：像素"稳定"要 5–7 帧

上面的帧率是"画面被驱动了多少次"，不等于"像素到位了"。一帧只推 20 ms，像素要 100–200 ms 才完全反转，所以实践中每个变化像素要连续推 **5–7 帧**（剂量模型）。

换算过来：

| 帧率 | 物体从黑到白所需时间 | 观感 |
|---|---|---|
| 30 fps | 5–7 帧 = **170–230 ms** | 快速横向移动会拖出"彗尾" |
| 20 fps | 5–7 帧 = **250–350 ms** | 只适合慢速/离散变化 |

**这就是墨水屏做游戏的真实约束**：不是"帧率不够"，而是"运动物体的边缘会拖着半透明的影子"。上游所有项目（SmoothEPD / InkBoy / PaperBoy）的 demo 都是**大色块、慢速运动、离散状态变化**，不是巧合。

### 1.5 什么样的 2D 游戏适合这块屏

| 适合 ✅ | 勉强 ⚠️ | 不适合 ❌ |
|---|---|---|
| 解谜、推箱子、棋类、卡牌 | 平台跳跃（慢速卷轴） | 弹幕、横版飞行射击 |
| 回合制 RPG、战棋 | 俯视角动作（移动慢） | 需要渐变/半透明的画面 |
| 文字冒险、视觉小说 | 像素风跑酷（限速） | 粒子特效、光晕 |
| 桌面/棋盘/益智 | 节奏类（判定窗口 100 ms+） | 60 fps 手感依赖型 |

## 2. Godot 能不能"移植"上去

### 2.1 结论：不能"移植"，只能"重写"

Godot 4 对运行环境的要求是：一个带 MMU 的操作系统、GPU（GLES3/Vulkan）、几百 MB 内存。ESP32-S3 是 **512 KB SRAM + 无 MMU 的 MCU**，差 2–3 个数量级。

所以"把 Godot 游戏搬到墨水屏掌机"只有三种真实路径：

| 路径 | 做法 | 你的 Godot 工程 | 工程量 | 帧率 |
|---|---|---|---|---|
| **A 重写（C/C++）** | 自建微型 2D 引擎，游戏逻辑用 C 重写 | 只作为设计稿/素材源 | 小游戏 1–3 周/个 | 18–30 fps |
| **B 重写（C 引擎 + Lua 逻辑）** | 引擎用 C，玩法逻辑用 Lua（语法接近 GDScript） | 逻辑可"翻译"，不是重设计 | 小游戏 1–2 周/个 | 16–28 fps |
| **C 换平台（RK3566 + Linux 跑 Godot）** | 保留 Godot 工程，只换显示后端 | 几乎原样 | 3–6 个月（驱动+系统） | 15–20 fps |

### 2.2 逐项对照：Godot 的东西在 MCU 上怎么办

| Godot 特性 | 在 ESP32-S3 上 | 替代方案 |
|---|---|---|
| GDScript | 无解释器 | 重写 C，或嵌 Lua 5.4 |
| Scene / Node 树 | 无 | 实体数组 + 简单场景栈 |
| Sprite / AnimatedSprite | 可 | 位图 blitter + 帧表（查表拷贝） |
| TileMap | 可 | tile blitter（15 KB 帧缓冲随便画） |
| 2D 物理（RigidBody/Area） | 无 | 自己写 AABB / 网格碰撞 |
| Shader / CanvasItem 材质 | 无 GPU | 预烘焙，或 CPU 逐像素（很慢） |
| 粒子 | 勉强 | 少量 1bit 图案，或干脆不做 |
| 半透明 / 渐变 | 差 | 4×4 Bayer 抖动成网点 |
| 字体 | 可 | 点阵字库（12/16/24 px） |
| 音频 | 可 | PWM / PDM / I2S + ES8311 |
| 存档 | 可 | SD 卡 / NVS |
| 输入 | 可 | 按键矩阵 |

### 2.3 美术资产是最大的隐藏成本

Godot 里的美术通常是：PNG 图集、带抗锯齿的矢量图、渐变背景、发光叠加。搬到 1bit 400×300 上：

- **图集要重新量化**：RGBA → 1bit（阈值 + 抖动），或者 4 灰（2bit）；
- **抗锯齿边缘会变成"毛边"**：要么接受，要么按 1bit 重新画；
- **渐变会变成网点**：Bayer 抖动在静态画面上很好看，动起来会"爬行"（图案随物体移动而闪烁）；
- **透明叠加基本不可用**。

实践建议：**按 400×300 / 1bit 重新画一遍素材**，而不是压缩现有素材。这反而是这个平台的风格来源——像早期的 Macintosh / Playdate。

### 2.4 工作量估算

| 游戏规模 | GDScript 行数 | 重写为 C | 说明 |
|---|---|---|---|
| 小（单一玩法、无物理） | < 1 500 | 1–2 周 | 引擎一次写好，后面复用 |
| 中（多场景、状态机、存档） | 1 500–5 000 | 3–6 周 | 主要花在 UI 和存档 |
| 大（物理、程序化、特效） | > 5 000 | 不建议 | 收益不匹配 |

**引擎部分（一次性投入）**：帧缓冲/双缓冲、blitter、tilemap、输入、音频、场景栈、资源打包 —— 约 3–4 周，之后每个游戏只写玩法。

## 3. 三条路径怎么选

| | A 重写 C | B C + Lua | C RK3566 + Godot |
|---|---|---|---|
| 保留 Godot 工作流 | ❌ | ❌ | ✅ |
| 开发迭代速度 | 慢（编译烧录） | 快（改脚本即可） | 最快（热重载） |
| 帧率上限 | 30 fps | 28 fps | 20 fps（受 EPD 限制） |
| 续航 | **数周** | 数周 | 数小时 |
| 开机 | < 1 s | < 1 s | 10–20 s |
| 成本 | ¥200 | ¥200 | ¥600+ |
| 技术含量（对简历/毕设） | 高（自研引擎） | 高 | 中（系统集成） |
| 风险 | 低 | 中（Lua 性能） | 高（内核/电源/散热） |

**我的判断**：如果游戏是你自己写的，**A 或 B 更划算**——重写成本可控，而且能吃到墨水屏的两个独有优势：**静态画面零功耗**（你可以做一个"放桌上永远显示当前关卡"的游戏）和**瞬时切场景**（不需要加载画面）。

只有在"必须继续用 Godot 迭代、且游戏已经很大"的情况下，C 才值得。

## 4. 需要你确认的三件事

1. **游戏类型与规模**：是解谜/战棋/文字类，还是平台跳跃/动作类？代码量大概多少？
2. **能否接受重写**：把 GDScript 翻成 C/Lua，还是必须沿用现有 Godot 工程？
3. **美术风格**：像素图、矢量扁平、还是带渐变/发光？

这三个答案会直接决定选 A/B/C 中的哪条，以及第一个游戏该选哪个来做验证。

## 5. 下一步（不管选哪条都成立）

1. **M0 加一项硬指标**：在 4.2" 上实测单帧扫描时间（用 1 帧 LUT + 秒表/逻辑分析仪），把上面表里的"15/30 ms"换成真数；
2. 同时测 SPI 在 20/40 MHz 下的误码率，确定安全时钟；
3. 写一个 400×300 的 1bit 帧缓冲 + 移动方块 demo，直接看"拖影有多长"——这个观感比任何参数都重要。
