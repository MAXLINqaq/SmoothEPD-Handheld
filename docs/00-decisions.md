# 00 · 决策记录（ADR）

> 每个决策写清楚"为什么"，以及"什么情况下该复审"。决策可以改，但要有理由地改。

## ADR-001 · 屏幕选型：4.7" 为主力，4.2" 做验证

**日期**：2026-10-29 · **状态**：已定

**背景**
- 需求：阅读（正文字体要清晰）+ 游戏（高刷不可舍弃）。
- 帧率天花板 ≈ 1 /（行数 × 行周期），像素数决定带宽 —— 见 [01 原理](01-principles.md#7-帧率天花板两个硬约束)。

**候选**

| 屏 | 行数 | PPI | 全屏 1bit 帧率 | 价格 | 结论 |
|---|---|---|---|---|---|
| 4.2" 400×300 | 300 | 140 | ~30 fps | ¥70–90 | ✅ 验证机 |
| **4.7" ED047TC1 960×540** | **540** | **234** | **~30–57 fps** | **¥70–120** | ✅ **主力** |
| 6" 1024×758 | 758 | 212 | ~13 fps | ¥80–180 | 备选（GBA 4× 整数缩放最优） |
| 6" 300 PPI | 1072 | 300 | ~9 fps | ¥200+ | 二代 |

**决定**
1. **M0–M2 用 4.2" 400×300（SPI，UC8176）**做验证机；
2. **M3 起换 4.7" ED047TC1（960×540，并口 40 pin）**做主力；
3. 同时买一块 **1.54" 200×200（SSD1681）**，只作为**参照物**——SmoothEPD 和 InkBoy 都在这个型号上调好了参数，遇到问题时可以对照排除"是屏的问题还是我的问题"；
4. 6" 1024×758 保留为备选：它的唯一优势是 GBA 可以 4× 整数缩放（960×640），代价是全屏帧率只有 ~13 fps。

**理由**
- 4.7" 是"能读整页正文"和"能跑 30 fps"的唯一交点；¥70 的价格让它可以用作可消耗的实验品；
- 4.2" 便宜、SPI 简单、例程多，适合把波形引擎先跑通；
- 用户明确表示"高刷不可舍弃"，因此排除 6"/7.8" 作为首版主力。

**影响**
- 主力屏是并口裸屏 → M3 必须解决 TPS65185 高压电源与 16 bit 时序（或买现成驱动板）；
- 4.7" 是 16:9，游戏画面不会占满全屏 → 见 ADR-003。

**复审条件**：4.2" 上跑不出 ≥ 20 fps，或 4.7" 面板实际行周期远大于 33 µs。

## ADR-002 · 起步硬件：ESP32-S3-DevKitC-1 + 微雪 4.2" 模块

**日期**：2026-10-29 · **状态**：已定

**决定**

| 件 | 型号 | 参考价 | 说明 |
|---|---|---|---|
| 主控板 | **ESP32-S3-DevKitC-1（N16R8）** | ¥65 | 16 MB Flash + 8 MB **八线** PSRAM |
| 验证屏 | 微雪 4.2inch e-Paper Module（400×300，UC8176） | ¥85 | 8 pin SPI，带电平转换和升压 |
| 参照屏 | 微雪 1.54inch e-Paper Module V2（200×200，SSD1681） | ¥35 | 与 SmoothEPD/InkBoy 同型号 |
| 杂项 | 杜邦线、面包板、USB-C 数据线 | ¥25 | |

**为什么不选别的板子**
- **必须八线 PSRAM**：逐像素状态 1.5 MB 要放 PSRAM，四线 PSRAM 带宽只有八线的一半，帧率会被内存拖死；
- **必须 16 MB Flash**：点阵字库 + 书籍缓存 + 双 OTA 分区；
- **必须引出足够 GPIO**：M3 的并口要 16 bit 数据 + CKV/SPH/LE/STV + 控制，共 21+ 根。DevKitC-1 两组 22 pin 排针刚好够（epdiy V7 也是用 S3 做 16 bit 并口，已验证可行）；
- 比它便宜的合宙/微雪核心板也能用，但排针间距和 USB 串口调试便利性差一些，不值得省这 ¥20。

**接线（M0）**

```
4.2" 模块        ESP32-S3
VCC     ────────  3V3
GND     ────────  GND
DIN     ────────  GPIO11 (MOSI)
CLK     ────────  GPIO12 (SCK)
CS      ────────  GPIO10
DC      ────────  GPIO9
RST     ────────  GPIO8
BUSY    ────────  GPIO7   ← 必须接 EXTI，用中断等
```

**复审条件**：4.2" 模块的实际控制器不是 UC8176（有些批次是 SSD1619），LUT 寄存器不同。

## ADR-003 · 游戏画面：整数倍缩放 + 局部窗口，不追全屏

**日期**：2026-10-29 · **状态**：已定

**背景**：4.7" 是 960×540 的 16:9，而目标机种的分辨率是：

| 机种 | 分辨率 | 比例 | 4.7" 上最大整数倍 | 实际占用 |
|---|---|---|---|---|
| GB | 160×144 | 10:9 | 3× | 480×432 |
| GBA | 240×160 | 3:2 | 3× | **720×480** |
| NES | 256×240 | 16:15 | 2× | 512×480 |
| SNES | 256×224 | 8:7 | 2× | 512×448 |

**决定**
1. **只做整数倍最近邻缩放**，非整数倍在 1bit 屏上会出现像素宽度不均的"抖动感"；
2. 游戏画面**靠上居中**，下方留给状态栏（电量/帧率/存档），这正是用户提出的"上半部分方形区域"方案；
3. 局部窗口只扫描游戏区那 480 行（而不是 540 行），帧时间同比缩短 ~11%；
4. 不追求全屏游戏——全屏 60 fps 需要面板行周期 ≤ 30 µs，超出 4.7" 的规格。

**影响**：`epd_present()` 的 `dirty` 矩形直接作为 partial window，游戏模式下窗口固定为 `(120, 20) – (840, 500)`。

## ADR-004 · Android：暂不进入主线，保留三条路径

**日期**：2026-10-29 · **状态**：待复审（M5 后）

**背景**：用户希望"正版阅读"，可能需要安装 APK。这会把项目从"单片机 + 显示驱动"变成"Android 显示栈移植"。

**结论摘要**：Android 与 30 fps 高刷在自制设备上**同时成立的成本极高**，建议分设备解决。详细分析见 [06 Android 路线](06-android.md)。

**三条路径**
| 路径 | 硬件 | 工作量 | 刷新表现 | 结论 |
|---|---|---|---|---|
| A 双机 | DIY 掌机 + 现成 Android 墨水屏 | 0 | 厂商级 | ✅ 推荐 |
| B Linux + 网页版 | RK3566 + EBC | 3–6 个月 | 100–250 ms | 可行，无反 APK |
| C 自制 Android | RK3566 + EBC + HWC HAL | 6–12 个月 | 仍达不到 30 fps | 研究级 |

**复审条件**：M5 整机完成后，如果阅读内容确实被"正版 App"卡住，再启动路径 B。

## ADR-005 · 放弃阅读器定位，改为"高刷 2D 游戏掌机"

**日期**：2026-10-29 · **状态**：已定（推翻 ADR-001 的部分结论）

**背景**：用户明确"阅读可以让位，高刷不能让位"，且游戏内容不是 GB/GBA 模拟器，而是**自己用 Godot 做的 2D 游戏**。

**决定**
1. **移除阅读器功能线**：M4 从"TXT/EPUB 排版"改为"第一个自研游戏"；
2. **主力屏改为 4.2" 400×300**：300 行比 4.7" 的 540 行快约 1.8 倍，是全屏帧率最高的可用尺寸；
3. 4.7" 960×540 降级为"可选升级"（想要更大画面时换，帧率 ~15 fps）；
4. 6" / 7.8" 从路线图中移除；
5. 阅读需求由另一台设备承担（见 [06 Android](06-android.md) 路径 A）。

**影响**
- 硬件大幅简化：SPI 单屏、无高压电源、无 TPS65185、无并口时序 → M3 的难度从 ★★★ 降到 ★；
- 帧率目标改为 **全屏 20–28 fps、局部窗口 30+ fps**（见 [07 Godot 移植](07-godot-port.md)）；
- 游戏设计必须适配墨水屏：大色块、慢速运动、离散状态变化。

**复审条件**：如果实测 4.2" 单帧时间显著优于 30 ms，再评估回到 4.7"。

## ADR-006 · 游戏运行时：重写 vs 保留 Godot

**日期**：2026-10-29 · **状态**：**待定**（等用户提供游戏类型/规模/美术风格）

**三个候选**

| 路径 | 描述 | 前提 |
|---|---|---|
| A | ESP32-S3 上用 C 重写，自研微型 2D 引擎 | 接受重写 |
| B | C 引擎 + Lua 脚本承载玩法逻辑 | 接受重写但想保留"脚本迭代"的爽感 |
| C | RK3566 + Linux 直接跑 Godot，自写 EPD 显示后端 | 必须沿用现有 Godot 工程 |

**评估依据**见 [07 Godot 移植](07-godot-port.md)。**结论倾向 A 或 B**：Godot 只作为设计与素材来源。
